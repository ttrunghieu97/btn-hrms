# HRMS Backend Business Readiness & Frontend Alignment Matrix

## 1. Classification & Readiness Status Legend

| Status | Meaning |
|---|---|
| `VERIFIED` | Core domain rules, state transitions, API/error contracts, RBAC/ABAC scope, DB transaction boundaries, and automated unit/contract/live-DB tests are verified in source code and ready as the source of truth for Frontend operation. |
| `PARTIAL` | Technical architecture and core workflows are implemented and verified, but optional business extensions (`PD-01`..`PD-03`) await Product Owner confirmation. |
| `BLOCKED` | Production operation is blocked until a mandatory statutory/business policy (`PD-04` payroll deduction formula) is approved by Product Owner / Finance and implemented. |
| `MISSING` | Capability is not implemented in Backend. |
| `DEFECTIVE` | Confirmed bug, authorization risk, or data integrity defect remains unresolved. |
| `UNVERIFIED` | Code exists in repository, but runtime verification is incomplete. |
| `NOT_APPLICABLE` | Outside current product scope. |

## 3. Open Product Owner Decisions (`PD-01` to `PD-04`) — Detailed Impact & Options Analysis

### `PD-01` — Probation Evaluation & Extension Workflow
- **Current Behavior**:
  - `employees.status` supports `'probation'` and `'working'`, with `employees.probationEndDate` (`date`) and `employmentRecords.confirmedAt` (`date`).
  - Confirming probation is executed via `PUT /api/v1/employees/:id/change-status` (`ChangeEmployeeStatusUseCase` -> `EmployeeLifecycleService.changeStatus` with `{ status: "working", effectiveDate, reason }`), which sets `employmentRecords.confirmedAt = today` and stages `EmployeeStatusChangedEvent`.
  - Failing probation is handled via `PUT /api/v1/employees/:id/terminate` or `POST /api/v1/employees/:id/schedule-termination`.
  - There is no multi-step probation evaluation scorecard or formal probation extension tracking (`extensionCount`, `previousProbationEndDate`).
- **Impact**:
  - **Backend**: Would require a new `ProbationEvaluationUseCase` / `ExtendProbationUseCase` if formal evaluation approval or extension limits (e.g., max 1 extension under Vietnam Labor Code Art. 25–27) are required.
  - **Database**: Would require `probation_evaluations` table or `probation_extension_count` column on `employment_records`.
  - **API**: Would add `POST /api/v1/employees/:id/probation/extend` and/or `POST /api/v1/employees/:id/probation/evaluate`.
  - **Frontend**: Employee Detail lifecycle hero currently provides direct status change (`probation -> working`) and termination actions.
- **Options**:
  - **Option A (Keep Current Direct HR Confirmation + Optional Date Edit)**: HR updates `probationEndDate` via profile edit if extended, and confirms probation via `PUT /api/v1/employees/:id/change-status`. *Pros*: Zero schema/API churn; works today. *Cons*: No structured audit of probation extension count or manager evaluation form.
  - **Option B (Add Formal Probation Extension & Evaluation Workflow)**: Enforce max 1 extension (<=60/30/6 days by role level) and manager scorecard before HR confirmation. *Pros*: Full statutory compliance and auditability. *Cons*: Requires PO approval of scorecard template and legal extension rules.
- **Required from Product Owner**: Confirm whether Option A is sufficient for current release or specify evaluation criteria and extension limits for Option B.

### `PD-02` — Scheduled Transfer Application (Manual HR Trigger vs Automated Cron Job)
- **Current Behavior**:
  - When HR approves a transfer (`POST /api/v1/employees/:id/transfers/:instanceId/hr-approve`):
    - If `effectiveDate <= today`, `ApproveTransferUseCase` immediately calls `ApplyTransferUseCase.execute(instanceId)` and completes the transfer.
    - If `effectiveDate > today`, `ApproveTransferUseCase` transitions the workflow instance to `currentState = "approved"`, `status = "active"`.
  - Once `effectiveDate <= today`, HR can apply the transfer via `POST /api/v1/employees/:id/transfers/:instanceId/apply` (exposed in the Frontend via the **"Áp dụng ngay"** button on `EmployeeLifecycleWorkflowHero`).
  - Unlike `TerminationSchedulerJob` (`@Cron("5 0 * * *")`), there is currently no automated daily cron job that auto-applies approved transfers when `effectiveDate` arrives.
- **Impact**:
  - **Backend**: Adding a daily `@Cron` job (`TransferSchedulerJob`) would query `workflow_instances` with `workflowType = 'employee_transfer'`, `currentState = 'approved'`, `status = 'active'`, and `context.effectiveDate <= today`, invoking `ApplyTransferUseCase.execute(instanceId)`.
  - **Database / API**: No schema or endpoint changes required.
  - **Frontend**: The manual **"Áp dụng ngay"** button remains useful as an immediate override on the effective date.
- **Options**:
  - **Option A (Manual HR Apply on Effective Date — Current)**: HR clicks "Áp dụng ngay" on/after `effectiveDate` after verifying physical handover. *Pros*: Prevents premature org/access switches if handover is delayed. *Cons*: Requires manual HR action on effective date.
  - **Option B (Automated Daily Cron + Manual Button)**: Auto-apply at `00:10` daily on `effectiveDate`, while keeping the manual button. *Pros*: Zero manual toil for future-dated transfers. *Cons*: Auto-switches department/access even if physical transfer is postponed without cancelling the workflow.
- **Required from Product Owner**: Confirm whether approved future-dated transfers should auto-apply via daily cron (Option B) or require explicit HR confirmation on effective date (Option A).

### `PD-03` — Employee Self-Service Resignation Request
- **Current Behavior**:
  - All termination flows (`PUT /api/v1/employees/:id/terminate` and `POST /api/v1/employees/:id/schedule-termination`) are HR-initiated and guarded by `EmployeePolicies.edit` / `EmployeePolicies.terminate`.
  - Self-service employees (`/account/profile`) cannot submit a resignation request or trigger notice-period calculation.
- **Impact**:
  - **Backend**: Would require a self-service endpoint (`POST /api/v1/employees/me/resignation-requests`) wired to `platform-approval-engine` or `platform-workflow-engine`, transitioning into `ScheduleTerminationUseCase` upon HR approval.
  - **Database**: Can reuse `workflow_instances` or `approval_requests` with a `resignation_request` definition.
  - **Frontend**: Would add a "Gửi đơn xin thôi việc" dialog in self-service profile and an approval view for Managers/HR.
- **Options**:
  - **Option A (HR-Initiated Termination Only — Current)**: Employees submit resignation via external/offline channels or general requests, and HR records Immediate or Scheduled Termination in HRMS. *Pros*: Simple, zero risk of accidental self-termination workflows. *Cons*: Manual intake by HR.
  - **Option B (Self-Service Resignation Workflow)**: Employees submit resignation with requested `lastWorkingDate` and `reason`, routed through Manager -> HR approval, automatically scheduling termination on approval. *Pros*: End-to-end digital employee experience. *Cons*: Requires PO definition of notice-period rules (e.g., 30/45/3 days by contract type).
- **Required from Product Owner**: Confirm whether self-service resignation is in scope and specify notice-period validation rules per `contractType`.

### `PD-04` — Statutory Payroll Calculation Formula (BHXH / BHYT / BHTN & Personal Income Tax) — **PRODUCTION BLOCKER (`BLOCKED`)**
- **Current Behavior**:
  - Payroll run orchestration, snapshot lineage, Segregation of Duties (SoD), payslip publishing, and final settlement workflows are implemented and verified against live PostgreSQL in `modules/payroll` (`phase6a/6c/6e/6g-payroll-integrity.spec.ts`).
  - `CalculatePayslipService` (`apps/api/src/modules/payroll/services/calculate-payslip.service.ts`), `GeneratePayrollRunUseCase` (`apps/api/src/modules/payroll/payroll-runs/use-cases/payroll-runs.usecases.ts`), and `CalculateFinalSettlementUseCase` (`apps/api/src/modules/payroll/use-cases/calculate-final-settlement.usecase.ts`) compute deductions using a temporary provisional formula and explicitly stamp `isProvisional: true` and `calculationStatus: "PROVISIONAL_POLICY_UNCONFIRMED"` (`PAYROLL_CALCULATION_STATUS`) across `PayrollRunResponseDto` (`PayrollRunMapper.toDto`), `PayrollResponseDto` (`PayrollMapper.toResponseDto`), and `PayslipResponseDto` (`PayslipMapper.toResponseDto`).
  - All backend and frontend mappers enforce fail-closed semantics: any run or payslip lacking an explicit `calculationStatus === "CONFIRMED"` and `isProvisional === false` is treated as provisional—even if mutable `notes` or `metadata` are cleared.
