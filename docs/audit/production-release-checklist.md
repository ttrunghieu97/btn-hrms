# HRMS Production Release Checklist & Go-Live Preflight (Evidence-Only Report)

## 1. Executive Preflight Summary & Methodology

This document records the **Evidence-Only Production Go-Live Preflight** for the HRMS monorepo (`@project/api`, `@project/permissions`, `frontend`). Every control, script, test, and operational requirement is classified strictly as:

- **`VERIFIED`**: Proven directly by repository source code and executed automated tests or local isolated drills in this workspace, with exact file paths, line numbers, and command outputs cited.
- **`BLOCKED`**: Intentionally prevented from production execution by active fail-closed software guards pending mandatory business/statutory sign-off (`PD-04`).
- **`NOT VERIFIED`**: Not proven by repository code or local test commands because it depends on target staging/production infrastructure, external KMS/disk/TLS configuration, live production secrets, or operator execution in the target deployment environment.

> **Evidence Rule**: Passing unit, integration, or example-config test commands prove **code and contract behavior**, not that a live production deployment, disk encryption setup, TLS certificate termination, or production database restore has been executed.

## 3. Section 2 — Production Configuration Verification

### 3.1. Repository Validation Procedures
There are **two distinct environment validation mechanisms** in the repository:

1. **Static Key-Presence Check (`scripts/deployment/check-env.mjs`)**:
   - Invoked via `pnpm deployment:check-env -- --mode=example` (validates `.env.example`, `apps/api/.env.example`, and `apps/web/.env.example`) or `pnpm deployment:check-env` (validates `process.env` in the current shell).
   - Checks only that required key names are non-empty:
     - **Root (`.env.example`)**: `APP_TIMEZONE`, `NEXT_PUBLIC_APP_TIMEZONE`, `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`, `PII_ENCRYPTION_KEY`, `APP_URL`, `AUTH_JWT_SECRET`, `AUTH_JWT_REFRESH_SECRET`, `AUTH_DEFAULT_PASSWORD`.
     - **API (`apps/api/.env.example`)**: `NODE_ENV`, `HOST`, `PORT`, `APP_URL`, `DATABASE_URL`, `DATABASE_DIRECT_URL`, `REDIS_URL`, `STORAGE_BACKEND`, `STORAGE_BUCKET`, `STORAGE_S3_ENDPOINT`, `STORAGE_S3_ACCESS_KEY`, `STORAGE_S3_SECRET_KEY`, `AUTH_JWT_SECRET`, `AUTH_JWT_REFRESH_SECRET`.
     - **Web (`apps/web/.env.example`)**: `NODE_ENV`, `PORT`, `HOSTNAME`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_API_BASE_URL`, `INTERNAL_API_URL`, `NEXT_PUBLIC_APP_TIMEZONE`.
   - **Important Limitation**: `scripts/deployment/check-env.mjs` checks **key presence only**; it does **not** reject placeholder values (such as `your_jwt_secret_here` or `BtnHrms2025!@#`) and does **not** check secret length or entropy.

2. **Runtime API Boot Validation (`apps/api/src/shared/config/validate-env.ts` — `validateEnv`)**:
   - Executed automatically when `@project/api` boots (`ConfigModule.forRoot({ validate: validateEnv })`).
   - Enforces:
     - Required keys: `DATABASE_URL`, `AUTH_JWT_SECRET`, `AUTH_JWT_REFRESH_SECRET`, `APP_URL`, `AUTH_DEFAULT_PASSWORD`.
     - Secret strength & placeholder rejection (`assertSecretStrength`, `lines 26-73`): Rejects values shorter than `32` chars for `AUTH_JWT_SECRET` and `AUTH_JWT_REFRESH_SECRET` (`12` chars for `AUTH_DEFAULT_PASSWORD`), rejects known placeholders/defaults (`your_jwt_secret_here`, `BtnHrms2025!@#`, `change-me`, `secret`, etc.), and requires `AUTH_JWT_SECRET !== AUTH_JWT_REFRESH_SECRET` (`lines 150-154`).
     - Production profile rules (`NODE_ENV === "production"`, `lines 180-241`): Requires valid `DATABASE_URL` (`postgres:`/`postgresql:`) and `REDIS_URL` (`redis:`/`rediss:`), requires `STORAGE_S3_URL` when `STORAGE_BACKEND=s3`, requires `VAULT_TOKEN` when `FEATURE_VAULT=true`, and **blocks `ALLOW_REMOTE_DB_RESET=true` in production**.
   - **PII Key Enforcement at DI Boot**: `EmployeesRepository` instantiates `new EmployeeEncryption()` (`employee-encryption.ts:24-44`), which throws `"PII_ENCRYPTION_KEY or PII_ENCRYPTION_KEY_V* must be set (at least 32 characters)"` if `PII_ENCRYPTION_KEY` (or `PII_ENCRYPTION_KEY_V1..V10`) is missing or shorter than 32 characters. Note that `apps/api/.env.example` omits `PII_ENCRYPTION_KEY` and `AUTH_DEFAULT_PASSWORD` (which are defined in root `.env.example`), so production API deployments must inject both from the root secret store.

## 4. Section 3 — PostgreSQL Recovery Verification

### 4.1. Distinction Between CLI Safety Unit Tests and an Actual Backup-and-Restore Drill

1. **CLI Fail-Closed Safety Guard Unit Tests (`scripts/deployment/restore-postgres.test.mjs`) — `VERIFIED` (`8/8 PASS`)**:
   - Command: `node --test scripts/deployment/restore-postgres.test.mjs` $\rightarrow$ **`8/8` tests passed (Exit `0`)**.
   - **What this proves**: Verifies only the **pre-execution fail-closed CLI guards** of `scripts/deployment/restore-postgres.mjs` (missing dump argument, missing `DATABASE_RESTORE_URL`, invalid URL protocol, `--target-db` mismatch, collision with active `DATABASE_URL` without `ALLOW_PRIMARY_DB_RESTORE=CONFIRMED_OVERWRITE_PRIMARY_DATABASE`, production block without `ALLOW_PRODUCTION_RESTORE=true`, missing `RESTORE_CONFIRM=I_UNDERSTAND_THIS_OVERWRITES_DATABASE_STATE`, and non-existent dump file).
   - **What this does NOT prove**: Every test in `restore-postgres.test.mjs` exits before invoking `pg_restore`. It is a unit test of CLI safety guards, **not** a backup-and-restore drill.

2. **Preflight Defect Discovered & Fixed in `scripts/deployment/backup-postgres.mjs` — `VERIFIED`**:
   - When executing a real backup during this preflight, `scripts/deployment/backup-postgres.mjs` initially failed with `pg_dump: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: FATAL: role "postgres" does not exist` because passing a `postgres://` URI via the `PGDATABASE` environment variable (without `--dbname`) causes `libpq` to treat the URI string as a literal database name on the local Unix socket instead of parsing the URI's host, port, user, and password.
   - **Fix Applied**: Updated `scripts/deployment/backup-postgres.mjs:18-26` to pass `"--dbname", databaseUrl` explicitly to `pg_dump` (matching `restore-postgres.mjs:106`).

3. **Isolated Local PostgreSQL 16.4 Backup-and-Restore Drill (`hrms` $\rightarrow$ `hrms_restore_drill`) — `VERIFIED` (Local Isolated DB Only)**:
   - **Host Binary Note**: `postgresql-client` (`pg_dump`, `pg_restore`, `pg_isready`) is **not installed on the local host OS PATH** (`/usr/bin`), but PostgreSQL 16.4 (`16.4-1.pgdg120+2`) `/usr/bin/pg_dump` and `/usr/bin/pg_restore` are present inside the running `btn-hrms-postgres` container.
   - **Executed Drill**:
     1. Executed `node scripts/deployment/backup-postgres.mjs` against local `hrms` (`127.0.0.1:5432/hrms`), producing a `1.2 MB` custom-format dump (`btn-hrms-2026-10-16T09-18-44-234Z.dump`).
     2. Created an isolated target database `hrms_restore_drill` on `127.0.0.1:5432`.
     3. Executed `DATABASE_RESTORE_URL=".../hrms_restore_drill" RESTORE_CONFIRM="I_UNDERSTAND_THIS_OVERWRITES_DATABASE_STATE" node scripts/deployment/restore-postgres.mjs --target-db=hrms_restore_drill <dump-file>`, completing with `[RESTORE] PostgreSQL restore completed successfully.` (Exit `0`).
     4. Verified schema compatibility and 1:1 row-count parity between `hrms` and `hrms_restore_drill` (`diff -u` $\rightarrow$ `EXACT_1_TO_1_MATCH`):
        - `public_tables`: `179` in `hrms` vs `179` in `hrms_restore_drill`

        - `payroll_periods`: `0` vs `0`, `payroll_runs`: `0` vs `0`, `payslips`: `0` vs `0`

4. **Production / Staging Backup-and-Restore Drill — `NOT VERIFIED`**:

   - **Required Operator Action Before Production Cutover**:
